# Aidee v0.1.0 Alpha 13

## Purpose

Upgrade an existing controller and every registered assistant to one verified
release through a repeatable desired-state update.

## Fleet update

- One preview and apply command manages the host, controller, and assistants.
- Apply requires explicit owner approval.
- The updater activates an exact clean tag, refreshes root-owned services,
  updates the pinned controller Hermes runtime, syncs controller knowledge and
  default crons, validates the assistant image, repairs assistant state, and
  verifies the result.
- Failed assistant container replacement restores the previous containers.
  Runtime data, configuration, credentials, memories, and repositories remain
  on their existing bind-mounted host paths.

## Assistant state

- Assistant instruction generation is shared by create and repair paths.
- Existing assistants receive Telegram choice and command approval behavior,
  repository workspace rules, software standards where applicable, and
  resumable onboarding instructions.
- `/opt/data/aidee/repos` is created with the assistant runtime ownership and
  mode.
- `/opt/data/aidee/onboarding-status.json` records identity, dashboard, model,
  Telegram, and repository setup without claiming external work succeeded.

## Controller scheduling

The daily update check and fleet watchdog are reconciled only in the central
controller Hermes runtime. The updater does not create assistant update jobs.

## Migration

Migration `001_alpha13_onboarding_registry` adds onboarding references to legacy
fleet registry entries. It writes a protected registry backup and records its
completion under `/var/lib/aidee/migrations`. Desired-state reconciliation
repairs missing runtime files without replaying every historical release.

## Rollback

Container replacement rolls back automatically before registry image fields
change. A host rollback may repoint `/opt/aidee/source` to the previous release.
Do not remove Alpha 13 onboarding or repository state during a rollback.
